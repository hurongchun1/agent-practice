# ReAct Agent：原理与当前实现

本目录用于从零理解并实现 ReAct Agent。ReAct 是 **Reasoning + Acting** 的缩写：它让大语言模型在解决问题时，不只进行推理，也可以调用搜索、计算器或业务 API 等外部工具，并根据工具返回的结果继续调整判断。

当前实现使用 JSON 解析模型动作；早期正则解析方案仅保留在 [REGEX_GUIDE.md](./REGEX_GUIDE.md) 中作为对照资料。

> 当前目录已经实现了工具定义与调度、LLM 调用、Action 解析和多轮循环。统一入口是 `run.py`。

## 0. 从整体上理解 ReAct

可以把 ReAct Agent 理解成一个**通过工具感知和影响外部环境，并根据环境反馈不断调整下一步行动的智能体**。它的实现主线可以概括为：

1. **确定工具**：先根据智能体要解决的问题，定义搜索、计算、数据库查询或业务 API 等工具。每个工具都要有明确的名称、功能描述、输入参数和执行函数。
2. **注册和调度工具**：当工具较多时，使用统一的工具执行器维护工具清单。它既能把“有哪些工具、每个工具能做什么”整理给模型，也能根据模型生成的 Action 找到并执行对应函数。
3. **编写提示词**：在提示词中定义智能体的角色、目标、可用工具、输出格式和每一轮应遵循的执行规则。
4. **保存上下文**：保留用户原始问题以及此前的 Action、Observation 等执行历史，让模型在下一轮能够基于已有结果重新判断。
5. **循环执行**：模型产生 Thought 和 Action，程序调度工具得到 Observation，再把 Observation 放回上下文；如此循环，直到模型输出 Finish 或达到最大执行步数。

需要特别区分“决策”和“调度”：

- **LLM 是决策者**：根据问题、提示词和历史记录决定是否调用工具、调用哪个工具以及传入什么参数。
- **工具执行器是调度者**：保存工具元数据，并将已经确定的工具名称映射到具体函数。它通常不负责推理，也不会自主决定下一步使用什么工具。

因此，完整结构不是简单地“模型调用工具”，而是以下几个组件共同构成的反馈系统：

```text
工具集合 ──注册──> 工具执行器 ──工具说明──┐
                                        │
用户问题 ────────────────────────────────┤
历史记录 ────────────────────────────────┤
                                        ▼
                                提示词 + LLM（决策）
                                        │
                                      Action
                                        │
                                        ▼
                                工具执行器（调度）
                                        │
                                   Observation
                                        │
                                        └──写入历史，进入下一轮
```

## 1. 为什么需要 ReAct

只依赖大语言模型通常存在两个问题：

- **纯推理无法访问外部世界**：模型可以分析问题，但不知道训练数据之后发生的新闻、价格或产品信息，也不能真正操作数据库和业务系统。
- **直接行动缺少反馈与纠错**：如果模型一次性决定并执行动作，就很难根据执行结果修正搜索词、切换工具或调整后续步骤。

ReAct 将推理和行动放进同一个反馈循环中：推理负责决定下一步做什么，工具负责与环境交互，工具结果再成为下一轮推理的依据。因此，它适合需要实时知识、精确计算或外部 API 的任务。

## 2. 核心循环

一次典型的 ReAct 轨迹由以下几个部分组成：

1. **Question（问题）**：用户希望智能体完成的任务。
2. **Thought（思考）**：模型分析当前已知信息，并决定是否需要使用工具。
3. **Action（行动）**：模型选择一个工具及其输入，例如 `Search[英伟达最新的 GPU 型号]`。
4. **Observation（观察）**：程序执行工具，将结果返回给模型。
5. **Finish（结束）**：模型判断信息已经足够，输出最终答案。

流程可以表示为：

```text
用户问题
   │
   ▼
Thought：分析问题和已有观察
   │
   ▼
Action：选择工具并给出参数 ──────┐
   │                            │
   ▼                            │
执行工具                         │
   │                            │
   ▼                            │
Observation：取得外部结果         │
   │                            │
   ├── 信息不足：写入历史并继续 ───┘
   │
   └── 信息充分：Finish[最终答案]
```

若用形式化方式描述，在第 `t` 轮中，模型会根据用户问题 `q` 和之前的行动、观察历史生成本轮思考与行动：

```text
(thought_t, action_t) = LLM(q, (action_1, observation_1), ..., (action_t-1, observation_t-1))
observation_t = Tool(action_t)
```

关键点是：`Observation` 必须追加到上下文中。否则模型看不到工具执行结果，也就无法形成闭环。

## 3. 一个简单示例

用户提问：`英伟达最新的 GPU 型号是什么？`

```text
Thought: 这是一个具有时效性的问题，需要查询最新网页信息。
Action: Search[英伟达最新的 GPU 型号是什么]

Observation: 搜索工具返回若干搜索摘要……

Thought: 已获得相关信息，但需要确认发布时间和产品定位。
Action: Search[英伟达官网 最新 GPU 发布时间 产品定位]

Observation: 搜索工具返回官网或新闻摘要……

Thought: 信息已经足够，可以整理答案。
Action: Finish[根据搜索结果生成的最终答案]
```

这个例子展示了 ReAct 与“一次搜索后立即回答”的区别：模型可以根据第一次观察决定继续核实，而不是被固定计划束缚。

### `search_tool.py`

`search(query)` 是智能体目前可使用的外部工具。它负责：

- 从环境变量读取 `TAVILY_API_KEY`；
- 通过 Tavily 请求搜索结果；
- 优先返回 Tavily 生成的综合答案；

- 将缺少密钥、无结果或调用异常转换成文本结果。

在 ReAct 流程中，该函数产生的返回值就是 `Observation`。

`ToolExecutor` 是工具注册表，负责将工具名称、用途说明和 Python 函数关联起来：

当前示例注册了 `Search` 工具，并演示了从 Action 到 Observation 的执行过程。这个模块相当于 ReAct 中模型与外部环境之间的适配层。

## 5. 完整 ReAct Agent 还需要什么

要从当前工具层扩展为完整智能体，还需要补齐以下组件：

### 5.1 提示词协议

提示词应包含工具列表、用户问题、历史轨迹和严格的输出格式。例如：

```text
可用工具：
{tools}

请按以下格式输出：
Thought: 对当前问题的分析
Action: ToolName[tool input]

当信息足够时输出：
Thought: 已经可以回答问题
Action: Finish[final answer]

Question: {question}
History: {history}
```

工具描述非常重要：模型主要依靠名称和描述判断何时调用哪个工具。

### 5.2 Action 解析器

程序需要把模型输出解析为结构化数据，例如：

```text
Search[查询内容]  -> tool_name = "Search", tool_input = "查询内容"
Finish[最终答案]  -> 结束循环并返回答案
```

教学实现可以使用正则表达式；生产环境更适合使用模型的结构化输出或 Function Calling，并对工具名、参数类型和必填字段进行校验。

### 5.3 Agent 主循环

主循环需要依次完成：

1. 将问题、工具说明和历史记录填入提示词；
2. 调用 LLM；
3. 解析 `Action`；
4. 若为工具调用，通过 `ToolExecutor` 执行；
5. 将 `Action` 和 `Observation` 写入历史；
6. 若为 `Finish`，返回最终答案；
7. 达到最大步数仍未完成时，安全终止。

伪代码如下：

```python
history = []

for _ in range(max_steps):
    response = llm(build_prompt(question, tools, history))
    action = parse_action(response)

    if action.name == "Finish":
        return action.input

    tool = tool_executor.getTool(action.name)
    observation = tool(action.input)
    history.extend([
        f"Action: {action.raw}",
        f"Observation: {observation}",
    ])

return "达到最大执行步数，任务未完成。"
```

## 6. 优势与局限

### 优势

- **能够使用外部知识和能力**：弥补模型知识过期、计算不精确和无法操作系统等不足。
- **动态规划**：每一步都能依据最新 Observation 调整下一步，而不是机械执行预先生成的完整计划。
- **便于调试**：可以从 Action、Observation 和状态历史中定位选错工具、参数错误或结果不足等问题。
- **易于扩展**：向工具注册表增加计算器、数据库或业务 API 后，主循环通常无需大幅修改。

### 局限

- **可能陷入循环**：模型会反复使用相同或相似的搜索词，因此必须设置 `max_steps`。
- **格式不稳定**：自由文本输出可能不符合 `Thought/Action` 协议，需要校验、重试或结构化输出。
- **工具结果并不天然可信**：网页摘要可能过时或错误，关键事实应使用可靠来源交叉验证。
- **成本和延迟较高**：每轮推理和工具调用都会增加耗时与费用。
- **存在安全风险**：工具调用可能带来提示注入、敏感信息泄露或破坏性操作，不能直接执行未经验证的参数。

## 7. 工程化注意事项

- 为循环设置最大步数、超时、重试次数和整体预算。
- 对工具名及输入参数做白名单和类型校验；高风险操作增加人工确认。
- 限制 Observation 的长度，并区分可信数据与网页中的非可信指令。
- 日志优先记录步骤编号、Action、Observation 摘要、耗时和错误。不要在面向最终用户的界面暴露模型的私密推理文本。
- 对搜索类答案保留来源链接，并对时效性或高风险信息进行交叉验证。
- API 密钥只通过环境变量读取，不写进代码、日志或版本库。
- 对同一问题多次运行可能得到不同轨迹，测试时应覆盖成功、无结果、工具异常、非法 Action 和超过最大步数等情况。

## 9. 习题一：计算器与逆波兰表达式

计算器工具的任务是为 ReAct Agent 提供稳定、精确的四则运算能力，避免让语言模型自己进行较长的数值计算。当前实现位于 `calculate_tool.py`，主要分为“分词—转换—求值”三个阶段。

### 9.1 为什么使用逆波兰表达式

人们通常使用中缀表达式，即运算符写在两个操作数中间：

```text
(123 + 456) * 789 / 12
```

直接对中缀表达式求值时，程序需要同时处理括号、乘除优先级和同级运算符的左结合规则。逆波兰表达式（Reverse Polish Notation，RPN）也叫后缀表达式，它把运算符写在操作数之后：

```text
123 456 + 789 * 12 /
```

转换完成后，括号和运算优先级已经体现在 token 的顺序中，求值阶段只需要一个数字栈，不再需要单独处理括号和优先级。

### 9.2 表达式分词

`tokenization_general()` 从左到右扫描原始字符串，将它拆分成数字、运算符和括号：

```text
输入：(123 + 456) × 789 / 12
tokens：["(", "123", "+", "456", ")", "*", "789", "/", "12"]
```

当前分词器的规则是：

- 跳过空格。
- 连续数字合并为一个非负整数 token，例如 `123` 不会被拆成三个数字。
- 支持 `+`、`-`、`*`、`/`、`(` 和 `)`。
- 先将中文输入中常见的 `×` 和 `÷` 归一化为 `*` 和 `/`。
- 遇到其他字符时抛出 `ValueError`。

### 9.3 中缀表达式转换为后缀表式

`calculate_expression()` 使用一个输出列表 `output` 和一个运算符栈 `operators`：

```text
数字
  → 直接追加到 output

左括号
  → 压入 operators，作为优先级处理的边界

右括号
  → 将运算符弹出到 output，直到遇到左括号
  → 丢弃这对括号，括号本身不进入后缀表达式

运算符
  → 将栈顶中优先级大于或等于当前运算符的元素弹出到 output
  → 再将当前运算符压栈
```

当前优先级表为：

```python
{
    "+": 1,
    "-": 1,
    "*": 2,
    "/": 2,
}
```

对栈顶使用“大于或等于”判断，使四个二元运算符保持左结合。例如 `8 / 4 / 2` 会转换为 `8 4 / 2 /`，即按 `(8 / 4) / 2` 计算。

所有 token 遍历完成后，再将 `operators` 中剩余的运算符依次弹出到 `output`。如果此时还存在左括号，则说明括号不匹配。

### 9.4 后缀表达式求值

`calculate()` 使用数字栈从左到右遍历后缀表达式：

```text
数字
  → 压入数字栈

运算符
  → 先弹出右操作数
  → 再弹出左操作数
  → 计算 left operator right
  → 将结果重新压栈
```

左右操作数的弹出顺序不能反转，因为减法和除法不满足交换律。遍历结束后，栈中必须恰好剩下一个值，否则说明表达式结构不合法。

完整示例：

```text
中缀：(123 + 456) * 789 / 12
后缀：123 456 + 789 * 12 /
结果：38069.25
```

### 9.5 异常与安全性

计算器不使用 Python `eval()`，而是只解析白名单内的数字、括号和四则运算符，避免用户输入被当作 Python 代码执行。当前会为下列情况抛出 `ValueError`：

- 存在非法字符。
- 左右括号不匹配。
- 运算符缺少操作数。
- 出现未知运算符。
- 除数为零。
- 遍历后栈中不是恰好剩下一个结果。

这些 `ValueError` 由 `ToolExecutor.execute()` 转换为 `INVALID_ARGUMENT`，再由任务二的纠错机制向模型返回 `RETRY_WITH_NEW_ARGUMENTS`。

### 9.6 当前实现边界

当前输入支持非负整数、括号和二元四则运算；除法会产生小数中间结果。暂不支持：

- 小数字面量，例如 `1.5 + 2.3`。
- 一元正负号，例如 `-3 + 5` 或 `2 * (-4)`。
- 幂运算、取模、函数、变量和科学计数法。

分词、中缀转后缀和后缀求值都只需要线性遍历，时间复杂度为 `O(n)`，额外空间复杂度为 `O(n)`。

## 10. 习题二：工具选择失败时如何引导智能体纠正？

本题的核心不只是“捕获异常”，而是把工具调用链路中的失败转换成模型下一轮可以理解并采取行动的 `Observation`，最终形成“识别—反馈—纠正—熔断”闭环。

### 10.1 按发生阶段和错误原因分类

“发生在什么时候”和“具体错在哪里”是两个维度。按发生阶段看：

| 阶段 | 程序能检查什么 | 错误码示例 |
| --- | --- | --- |
| 调用前 | 模型输出是否合法、工具名是否注册、参数是否满足基本要求 | `INVALID_MODEL_OUTPUT`、`TOOL_NOT_FOUND`、`INVALID_ARGUMENT` |
| 调用中 | 工具运行时是否抛出参数异常或执行异常 | `INVALID_ARGUMENT`、`EXECUTION_FAILED`、工具自定义错误码 |
| 调用后 | 工具虽返回成功，但结果是否相关、是否足以完成用户目标 | 当前由 Agent 根据 Observation 判断；必要时继续调用，不自动生成错误结果 |
| Agent 循环 | 连续失败或执行轮数超过上限 | `TOO_MANY_FAILURES`、`MAX_STEPS_EXCEEDED` |

工具名不存在属于**调用前**错误：程序在执行工具前查找注册表时发现。`TOOL_NOT_APPLICABLE` 表示工具虽然存在，但不适合用户目标；当前系统可将该错误映射为重新选择工具，不过需要工具或上层判断明确报告它。对于一般的“工具返回了无关结果”，当前由模型读取 Observation 后判断，提示词要求它不要因此直接结束。

### 10.2 统一的结构化结果

`common_result/tool_result.py` 定义了三个数据类：

- `ToolError`：记录错误阶段、错误码、原因和是否允许重试。
- `FailedCall`：记录失败调用的工具名和输入。
- `ToolResult`：作为工具调用成功或失败的统一结果。

它们的状态约束是：

```text
成功：ok=True，data 可以有值，tool_error 和 failed_call 为 None
失败：ok=False，tool_error 必须存在，data 为 None
```

`failed_call` 在能够解析出工具调用时存在；如果模型输出根本不是合法 JSON，系统无法得知工具名和参数，因此它可以为 `None`。`ToolResult.__post_init__()` 负责在运行时拒绝互相矛盾的字段组合，`frozen=True` 防止对象创建后被修改成非法状态。

### 10.3 工具执行器只返回事实

`ToolExecutor.execute()` 是统一的工具执行入口：

```text
调用前未找到工具 → TOOL_NOT_FOUND
参数校验失败     → INVALID_ARGUMENT
工具正常返回     → ok=True，data=工具结果
工具运行时异常   → EXECUTION_FAILED 或工具自定义错误码
```

执行器只负责描述客观结果，不负责编写给模型的提示。这样可以避免工具执行层与 ReAct 的提示策略耦合。

### 10.4 将错误转换成可执行的 Observation

`error_observation.py` 负责把失败 `ToolResult` 转换成面向模型的 Observation。失败反馈不能只说“调用失败，请重试”，而应该同时提供：

```text
发生了什么
为什么失败
是否允许重试
下一步应该采取什么动作
哪些失败行为不能原样重复
```

例如，模型选择了未注册的 `Math` 工具：

```json
{
  "ok": false,
  "error": {
    "stage": "tool_selection",
    "code": "TOOL_NOT_FOUND",
    "message": "调用的工具不存在",
    "retryable": true
  },
  "correction": {
    "action": "SELECT_ANOTHER_TOOL",
    "instruction": "请从当前可用工具中重新选择。",
    "constraints": ["不要再次选择不存在的工具"]
  },
  "failed_call": {
    "tool_name": "Math",
    "tool_input": "1+1"
  }
}
```

`correction.action` 不使用任意自然语言，而是限定在少量稳定动作中：

| 纠错动作 | 含义 |
| --- | --- |
| `FIX_MODEL_OUTPUT` | 按系统约定修正 JSON 输出 |
| `SELECT_ANOTHER_TOOL` | 重新选择工具 |
| `RETRY_WITH_NEW_ARGUMENTS` | 修改参数后重试 |
| `RETRY_LATER` | 针对临时性故障有限重试 |
| `STOP` | 停止调用并说明限制 |

其中 `TOOL_NOT_APPLICABLE` 与 `TOOL_NOT_FOUND` 都会使用 `SELECT_ANOTHER_TOOL`，但原因不同：前者是工具存在但不适用，后者是工具根本未注册。

### 10.5 已知策略与未知错误

系统不需要提前穷举所有异常文本，而是为稳定错误码配置少量可执行策略。当遇到没有预设的错误码时，当前实现默认返回 `STOP`，避免对支付、删除、发送消息等可能有副作用的操作盲目重试。

未知错误不应被忽略，应记录错误码、工具、阶段、出现次数和最终结果。当某个错误反复出现、含义稳定且可以安全分类时，再为它增加正式错误码和专用策略，而不是对每一条偶发异常都添加分支。

### 10.6 ReAct 纠错闭环

`ReActAgent` 将 `ToolResult` 转换成 JSON Observation 并写入 `History`，下一轮 Prompt 会同时包含工具列表、失败事实和纠错要求：

```text
模型生成 Action
  → 解析与校验
  → ToolExecutor.execute()
  → ToolResult
  → build_error_observation()
  → Observation 写入 History
  → 模型下一轮重新决策
```

工具调用成功后会清零连续失败计数；连续失败达到 `max_consecutive_failures` 后返回 `TOO_MANY_FAILURES`，整体步数达到 `max_steps` 后返回 `MAX_STEPS_EXCEEDED`，避免无限重试和无效工具消耗。

### 10.7 `retryable` 什么时候是 True 或 False

`retryable` 表示“这个错误是否可能通过下一轮纠正恢复”，不表示立即原样执行一次工具。

| 情况 | retryable | 原因与处理 |
| --- | --- | --- |
| 模型输出格式错误 | `True` | 模型可以按 JSON 规则重新输出 |
| 工具不存在 | `True` | 模型可以从可用工具中重新选择 |
| 参数为空或不合法 | `True` | 模型可以根据报错修改参数 |
| 明确的临时性执行失败 | `True` | 工具主动使用 `ToolExecutionError` 表明允许有限重试 |
| 工具缺少必要配置 | `False` | 修改参数或更换表达方式无法补齐系统配置 |
| 未知执行异常 | `False` | 系统无法确认重复调用是否安全或有效 |
| 权限、业务规则等确定性限制 | `False` | 重复调用不能改变限制条件 |

Agent 收到失败结果后的控制逻辑是：

```text
retryable=False
  → 生成包含 STOP 的 Observation
  → 立即返回失败结果，不再调用 LLM 或工具

retryable=True
  → 生成具体纠错动作并写入 History
  → 下一轮由模型修改输出、重新选工具或修改参数
  → 连续失败达到阈值后触发 TOO_MANY_FAILURES
```

当前示例中的具体取值如下：

```text
INVALID_MODEL_OUTPUT  → True  → FIX_MODEL_OUTPUT
TOOL_NOT_FOUND        → True  → SELECT_ANOTHER_TOOL
INVALID_ARGUMENT      → True  → RETRY_WITH_NEW_ARGUMENTS
临时 EXECUTION_FAILED → True  → RETRY_LATER
CONFIGURATION_ERROR   → False → STOP
未知 EXECUTION_FAILED → False → STOP
```

### 10.8 从输入到终止的完整闭环

```text
用户问题
  → LLM 输出 JSON
  → ReActAgent 校验模型输出
      ├─ 格式错误：INVALID_MODEL_OUTPUT，允许模型修正
      └─ 格式正确：提取 tool_name 和 tool_input
  → ToolExecutor.execute()
      ├─ 工具不存在：TOOL_NOT_FOUND
      ├─ 参数不合法：INVALID_ARGUMENT
      ├─ 工具主动报告异常：保留其 code 和 retryable
      ├─ 未知异常：EXECUTION_FAILED，默认不可重试
      └─ 执行成功：ToolResult(ok=True, data=...)
  → 失败结果转换为结构化 Observation
      ├─ retryable=True：写入 History，进入下一轮纠正
      └─ retryable=False：记录 STOP 后立即结束
  → 成功结果写入 History，模型检查结果是否相关、是否足够
      ├─ 不相关或不足：重新选工具或补充调用
      └─ 足以完成目标：finish
  → 连续可纠正失败达到阈值：TOO_MANY_FAILURES
  → 总步数达到上限：MAX_STEPS_EXCEEDED
```

`tests/` 使用预设响应的 `FakeLLM`，分别测试模型输出解析、工具执行和 Agent 闭环，不需要访问真实模型或搜索服务。

### 10.9 验收标准与实现边界

当前代码实现的处理路径：

- 选择未注册工具后，下一轮改用已注册工具。
- 输出非法 JSON 后，下一轮按约定修正输出。
- 工具参数错误时，返回 `RETRY_WITH_NEW_ARGUMENTS`。
- 连续失败达到阈值后安全终止。
- 不可重试错误和未知错误码使用 `STOP` 兜底。

当前没有独立的结果评估器，不能由程序自动断定一个成功结果在语义上是否相关；这一步由模型根据原问题和 Observation 决定。若模型或工具明确报告 `TOOL_NOT_APPLICABLE`，系统会返回“重新选择工具”的纠错 Observation。后续可以为工具补充适用场景说明，帮助模型更准确地选择。

## 11. 习题三：工具增加到 50～100 个时如何组织和检索？

### 11.1 问题分析

当工具只有少量时，把所有工具定义放进提示词很直观；但工具增加到 50～100 个后，继续全量注入会带来几类问题：

- **上下文负担变大**：工具描述和参数 Schema 占用输入 token，增加成本，也会挤压用户请求、历史轨迹和工具结果的空间。
- **选择容易混淆**：职责相近、描述不一致或边界模糊的工具会彼此干扰，模型可能选错工具或生成不合适的参数。
- **检索与维护复杂**：业务持续增加后，工具定义、权限、版本、适用范围和弃用状态都需要治理。
- **延迟可能增加**：如果每个请求都要让模型阅读很长的工具清单，或为每个子任务串行调用一次路由模型，端到端耗时都会上升。

因此，问题不只是“模型能否容纳 100 个工具”，而是如何让模型在不接触无关完整定义的情况下，仍能找到并正确调用需要的工具。工具发现会借鉴 RAG 的检索思路，但检索的对象是工具目录；它不应退化成把大量候选内容不加控制地塞回上下文。

### 11.2 分阶段的工具发现与加载

可以把工具选择设计成应用层与模型协作的多阶段流程：

```text
用户请求
  → 应用侧按身份、租户、权限、启用状态等元数据过滤
  → 识别意图；跨领域请求拆成有依赖关系的子任务
  → 对子任务批量检索工具目录，合并并去重候选
  → 检查候选是否覆盖用户明确提出的目标
  → 只加载候选工具的完整说明和参数 Schema 给模型
  → 模型决定调用及参数，应用校验并执行
  → 把 Observation 返回模型，继续决策并汇总结果
```

工具目录中的每项工具可以维护两层信息：

1. **轻量工具卡片**：名称、简短用途、领域、适用场景、关键词和权限标签，用于快速过滤与检索。
2. **完整工具定义**：详细说明、输入参数 JSON Schema、约束、示例和副作用信息，仅在工具进入候选集后加载到模型上下文。

这能减少每轮传入模型的定义量，但候选检索仍可能漏掉相关工具。因此要把检索视为“找候选”，不是最终决策；最后由模型结合完整说明和用户目标判断是否适用，应用侧再验证权限和参数。

### 11.3 权限、意图与候选检索

过滤顺序很重要。用户身份、租户范围、工具启用状态和权限属于应用能够确定的约束，应先在应用侧过滤；这既缩小候选范围，也避免向模型暴露不可用工具。权限检查必须在实际执行时再次进行，不能仅依赖模型没有看到该工具。

在剩余工具中，再根据用户请求识别意图或业务领域。对于单一目标，可以直接检索相关工具；对于明确包含多个动作或跨业务域的请求，可以先拆成子任务，再分别检索。例如“查明天上海天气，并找一家附近的素食餐厅”可以拆成天气查询和餐厅搜索两个子任务。

拆解不是越细越好：只拆出需要不同工具、业务域或独立结果的动作，避免把一个简单请求切成很多微小步骤。拆解时还要区分用户明确要求与系统推测的后续动作，不能擅自把“查找”扩展成“预订”或“下单”。

对于 Top-K 的担忧是合理的：固定取 Top-2 或 Top-3 可能漏掉正确领域，特别是跨域或表达含糊的请求。可以让检索器为每个子任务返回少量候选并按相关性排序，再做覆盖检查；若某个明确子任务没有对应候选、相关性不足或模型判断候选均不适用，就扩大候选范围、切换领域或向用户澄清。候选数量不必对所有请求固定相同，可以受上下文预算和置信度控制。

### 11.4 控制多意图请求的时间和成本

“拆成子任务”不等于每个子任务都要单独串行调用一次大模型。为了控制延迟，可以：

- 先用应用侧规则、关键词和元数据做轻量过滤，再只对难以判断的请求使用语义检索或模型路由。
- 一次识别出所有子任务后，批量检索它们的工具，并合并去重候选；避免反复加载相同工具定义。
- 对独立子任务并行检索或执行；存在依赖关系的任务按顺序执行，不能为了并行而破坏业务流程。
- 单意图、高置信度请求走轻量路径；只有多意图、低置信度或覆盖不足时才触发拆解和补充检索。
- 为候选工具数、检索轮次、模型调用次数和总延迟设置预算，并缓存稳定的目录索引或高频路由结果。

需区分**并行检索**和**并行执行**：前者是在工具目录里同时为多个子任务找候选；后者是执行已经选定的工具。即使子任务可以并行检索，执行阶段也要先判断它们是否互相独立，以及是否涉及有副作用的操作。

### 11.5 不同模型与工具调用接口

GPT、Qwen 等模型可以负责理解请求、判断是否需要工具、选择给定候选并生成参数，但“如何管理 100 个工具”通常仍是 Agent 框架或应用层的工程职责。不能假设模型本身会自动完成权限过滤、候选召回、工具版本管理或延迟优化。

如果模型服务提供延迟加载或工具搜索能力，可以由服务按需发现并加载工具；若接口只接受本次请求的工具列表，应用或 Agent 框架就需要自行实现工具目录、元数据过滤、候选检索和分阶段加载。不同模型与托管接口的能力并不完全相同，应以实际使用的 API 和框架为准。无论使用哪种模型，工具调用结果都应由应用校验：工具名是否允许、参数是否符合 Schema、用户是否有权执行，以及动作是否需要额外确认。

### 11.6 如何评估方案

不能只看 Top-K 命中率或模型是否成功调用了某个工具。可以选取真实的单意图、多意图、跨领域、模糊表达和无可用工具请求，比较“全量注入”“先路由再注入”“拆解后批量检索”等方案，并记录：

- **工具/领域召回率**：所需工具是否进入候选集，跨领域请求的每个明确子任务是否都有候选覆盖。
- **选择与执行质量**：最终工具选择正确率、参数校验通过率和端到端任务成功率。
- **错误类型**：漏召回、误召回、错选工具、参数错误、权限拒绝、重复调用和不必要的拆解。
- **资源开销**：输入 token、模型调用次数、工具检索耗时、端到端 P50/P95 延迟及成本。

最终目标是在给定延迟和上下文预算下，达到业务要求的召回率与端到端成功率。若拆解明显提高召回，却让常见简单请求也多出一次模型调用，就应改为只对复杂或低置信度请求启用拆解。

### 11.7 总结

我的方案是采用“**确定性过滤 + 意图路由/必要时拆解 + 批量检索候选 + 按需加载完整定义 + 校验执行 + 结果回传**”的分层机制。用户身份、权限、工具启用状态等由应用侧优先过滤；模型不必在每次请求中看到所有完整工具定义。跨业务域请求可以拆成有依赖关系的子任务，批量检索和去重候选，独立任务再并行处理。为了应对检索不精准，需要检查候选对用户目标的覆盖，并在必要时扩大检索或澄清；为了控制时间，则让简单请求走轻量路径，并限制额外调用和延迟预算。

这本质上借鉴了 RAG 的“先发现相关候选、再提供给模型”的思路，但必须用权限约束、覆盖检查、回退机制和评测指标控制召回风险与成本。它不是仅靠换一个更大的模型就能解决的问题，而是模型能力、工具目录质量和应用编排共同决定的工程问题。

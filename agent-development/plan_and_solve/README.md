# Plan-and-Solve：动态重规划思考记录

本文记录对 Plan-and-Solve 执行阶段失败处理的研究思考，重点讨论：**故障发生后，系统如何判断应该重试当前步骤、调整局部计划，还是重新规划整个任务？**

## 1. 问题背景：静态计划的局限

当前示例由 Planner 一次性生成步骤列表，再由 Executor 按顺序执行。Executor 会把原问题、完整计划、历史结果和当前步骤交给模型，但不会判断某一步的结果是否有效，也不会根据执行反馈修改后续计划。

这种实现适合步骤明确、执行结果可预期的简单任务。一旦遇到外部状态变化、工具失败或结果不符合目标，后续步骤仍可能沿着过时计划继续执行。例如：

```text
计划：查询航班 → 预订航班 → 预订酒店 → 租车 → 汇总行程
执行：所选航班售罄
静态执行：仍继续按原定抵达时间安排酒店和租车
```

问题不只是“步骤失败了”，而是失败可能改变后续步骤所依赖的条件。动态重规划机制需要读取执行结果，并决定计划应该如何变化。

## 2. 核心判断原则

执行遇到问题时，不应一律重做，也不应机械地继续原计划。系统应先判断结果偏差的类型、影响范围，以及哪些已完成结果仍然有效，再选择合适的恢复动作：

> **先分类故障，再分析依赖和影响范围，最后决定重试当前步骤、修订剩余计划，还是重新规划全局。**

判断时可以依次回答三个问题：

1. **发生了什么？** 是暂时性故障、当前方案不可行、输入或约束发生变化，还是结果成功但不满足目标？
2. **影响了哪些步骤？** 故障是否改变后续步骤的输入、约束、前置条件或可行性？
3. **哪些结果仍然有效？** 已完成结果是否依赖于已经失效的假设？仍有效的结果应保留，避免重复执行。

## 3. 故障类型与恢复策略

结合任务执行过程，可以先把遇到的问题归纳为四类。每一类对应不同的恢复动作：

| 问题类别 | 含义 | 示例 | 典型处理方式 |
| --- | --- | --- | --- |
| 步骤条件或当前方案不可行 | 当前步骤依赖的条件无法满足，原方案无法继续 | 选定的航班售罄 | 在当前步骤保留原目标和约束，重新寻找方案；新方案确定后检查后续依赖 |
| 计划依据的事实或需求发生变化 | 用户更新了要求，或计划所依赖的关键事实不再成立 | 用户要求比原计划提前一小时到达 | 更新受变化影响的计划；依据影响范围决定局部修订还是全局重规划 |
| 暂时性执行错误 | 执行失败来自可能短暂恢复的技术问题 | 接口偶然超时、短暂网络中断 | 在确认重试安全的前提下，有限次重试当前步骤 |
| 执行成功但结果不满足计划要求 | 工具正常返回结果，但结果未通过当前步骤的目标或约束检查 | 酒店预订成功，但超预算或离会议地点太远 | 当前步骤不能视为完成；调整条件或替代方案，并检查后续步骤是否受影响 |

这四类问题是对恢复决策的实用归纳，不意味着它们在所有系统中完全互斥。例如，用户更新到达时间后，可能导致原航班方案不再满足要求；酒店搜索结果不符合预算，也可能暴露出当前预算约束下没有可行酒店。系统应根据具体事件记录原因，而不是只贴一个模糊的“失败”标签。

另有权限拒绝、不可恢复错误或执行结果不确定等情况，应作为安全与异常处理：不能通过盲目重试绕过权限，也不能在交易状态不明时直接重复下单。系统应停止相关动作、查询实际状态或请求用户处理。

### 3.1 每类问题对应的重规划范围

- **步骤条件或当前方案不可行**：优先在当前步骤内寻找替代方案。例如航班无票时，保留“按日期、预算和到达要求完成北京到上海出行”的目标，重新查询其他航班；若飞机方案都不可行，再考虑用户允许的高铁等交通方式。替代方案确定后，再检查它是否改变后续步骤的输入和约束。
- **计划依据的事实或需求发生变化**：先定位变化影响的步骤，不能默认每次都推翻整份计划。比如用户要求提前一小时到达，可能需要更新交通安排，并调整依赖抵达时间的租车或酒店入住；如果变化影响出行日期、住宿日期和多个阶段的前置条件，才需要进行全局重规划。
- **暂时性执行错误**：如果错误确实可能暂时恢复，且重复操作不会造成重复预订、重复付款等副作用，就对当前步骤进行有限重试；设置重试次数、退避和超时边界。
- **执行成功但结果不满足计划要求**：结果虽然由工具成功返回，但当前步骤的目标尚未达成。例如酒店超预算时，应在住宿步骤调整筛选条件或搜索替代酒店，而不是把它记录为已完成；新结果可能会影响地点、入住时间或交通安排，因此还要检查相关后续步骤。

### 3.2 需求变化不等于自动全局重规划

“用户改变了要求”说明旧计划的某些输入需要更新，但重规划范围仍取决于影响范围。例如只把到达时间提前一小时，可能仅需调整机票选择和接机安排；如果连出行日期、会议日期和住宿天数都改变，则多个计划阶段都可能失效，需要重新规划全局。

因此，重规划范围不是由问题类别单独决定的，而要沿计划的依赖关系判断：

```text
发现偏差
  → 分类问题及原因
  → 找出变化的条件、输入或约束
  → 沿依赖关系定位受影响步骤
  → 保留仍有效的结果
  → 重试当前步骤 / 替换当前方案 / 局部修订 / 全局重规划
```

**判断原则：局部问题优先局部修订；只有用户目标、关键约束或多个步骤的前置条件整体改变时，才扩大到全局重规划。**

## 4. 故障影响范围：沿依赖关系判断

需要把计划表示为有依赖关系的步骤，而不只是一个字符串列表。每个步骤至少应说明：

- 执行目标与完成条件；
- 所需输入和前置步骤；
- 产生的结果，以及哪些后续步骤会使用它；
- 失败类型、是否可重试和安全限制。

若步骤之间的关系如下：

```text
确定日期 ──> 查询并选择航班 ──> 确认抵达时间 ──> 安排租车
                  │
                  └──────────────> 预订酒店
```

航班售罄时，当前航班选择需要重做；如果新航班仍在同一天、抵达时间没有改变，酒店选择结果可能仍然有效；如果抵达时间变化，则租车取车安排可能失效。重规划范围应由数据依赖和业务约束决定，而不是简单地从失败步骤开始重跑全部工作。

因此系统需要维护计划状态，例如：

```text
PENDING     尚未执行
IN_PROGRESS 正在执行
COMPLETED   已完成且结果有效
FAILED      执行失败，等待分类
BLOCKED     前置条件未满足
INVALIDATED 原结果因假设或输入变化而失效
SKIPPED     经重规划后不再需要
```

约束或前置结果变化时，可以将依赖它的后续步骤标记为 `INVALIDATED`，只重新执行受影响部分。

## 5. 一个决策流程

```text
步骤执行完成或失败
  → 校验结果是否满足该步骤的完成条件
  → 若是暂时性故障且重试安全：有限重试当前步骤
  → 若是信息缺失：请求补充或先完成信息收集
  → 若当前方案不可行：生成替代方案并更新局部计划
  → 根据依赖关系标记受影响的后续步骤
  → 保留仍有效的已完成结果，只重做失效步骤
  → 若关键目标、约束或多个阶段的前提改变：重新规划全局
  → 若不可恢复或风险不可控：停止并向用户说明
```

这不是要求每次都多调用一个模型。可确定的判断（例如超时、权限拒绝、参数校验失败、库存不足）应优先由应用和工具的结构化状态处理；模型更适合处理需要语义判断的“结果是否满足用户目标”“替代方案是否可接受”等问题。

## 6. 例子：航班售罄

假设任务是预订一次从北京到上海的商务旅行，包括机票、酒店和租车。原计划中酒店入住时间和租车取车时间都依据航班抵达时间。

1. **航班查询成功，但预订时该航班售罄。** 这不是网络瞬时故障，不应原样重试同一订单；应查询替代航班。
2. **替代航班时间相同或相近。** 重新确认酒店与租车安排仍满足原约束；若有效，可以保留已有结果。
3. **替代航班晚到数小时。** 依赖抵达时间的租车取车时间和酒店入住安排需要重新检查，必要时调整。
4. **没有符合用户约束的替代航班。** 应汇报可选项或请求用户放宽时间、预算等约束，不应自行改变用户的重要要求。

从这个例子可以看出，触发局部重规划的关键不是“航班步骤失败”本身，而是失败或替代方案是否改变了其他步骤的前置条件和约束。

## 7. 当前阶段的结论

动态重规划的重点不是在原计划后面追加一个“失败后再生成计划”的模型调用，而是建立一个有状态、可检查依赖关系的执行机制：

- 为步骤定义明确的完成条件和结构化结果；
- 区分可重试故障、可替代方案、缺失信息、约束变化和不可恢复错误；
- 根据步骤依赖判断影响范围；
- 保留仍然有效的已完成结果，只使失效结果无效；
- 只有影响范围足够大时才重新规划全局；
- 为重试次数、总步数、成本和高风险操作设置边界。

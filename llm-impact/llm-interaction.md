# 大语言模型交互：提示词工程与生成参数

大语言模型交互主要包含两个阶段：

```text
输入阶段：通过提示词说明希望模型完成什么
输出阶段：通过生成参数控制模型怎样选择下一个 token
```

提示词工程影响模型对任务的理解；`Temperature`、`Top-k` 和 `Top-p` 影响模型生成答案时的选词方式。它们都能改变最终回答，但作用位置不同。

## 1. 提示词工程

提示词（Prompt）是发送给大语言模型的输入内容。提示词工程不是寻找某句神奇口令，而是尽量清楚地告诉模型：

```text
要完成什么任务
可以使用哪些背景信息
必须遵守哪些限制
结果应该以什么形式输出
```

例如，下面的提示词信息不足：

```text
帮我写一份报告。
```

模型不知道报告主题、目标读者、篇幅、语气和必须包含的内容。补充信息后会更清楚：

```text
请为刚接触人工智能的大学生写一份 Transformer 入门报告。
控制在 1500 字以内，使用通俗中文。
先解释 Encoder 和 Decoder 的分工，再解释自注意力，
最后用“我喜欢吃苹果”给出完整示例。
使用 Markdown 二级标题，不展开复杂数学证明。
```

提示词越明确，模型越容易判断什么结果符合要求。

## 2. 怎样写出清晰的提示词

一个实用的提示词通常包含以下内容，但不是每次都必须全部使用。

### 2.1 任务

直接说明需要模型做什么：

```text
解释、总结、翻译、比较、分类、提取、改写、生成代码……
```

例如：

```text
请解释 Transformer 中掩码自注意力的作用。
```

### 2.2 背景

告诉模型当前场景和读者已经掌握的内容：

```text
读者已经理解普通自注意力，但不了解 Decoder。
这份内容将作为机器学习入门笔记使用。
```

### 2.3 约束

明确必须满足什么或不能做什么：

```text
不要推导复杂公式。
控制在 800 字以内。
所有示例使用同一句话。
```

约束应该具体、可检查。与其说“不要太复杂”，不如说“只解释概念，不推导公式”。

### 2.4 输出格式

说明结果应该怎样组织：

```text
先给结论，再分步骤解释。
使用 Markdown 表格比较概念。
最后给出三句话总结。
```

### 2.5 示例

当要求难以准确描述时，可以提供少量示例：

```text
示例输入：CNN
示例输出：像拿着小窗口观察图片，擅长提取局部特征。

现在请用相同方式解释 RNN。
```

示例可以帮助模型理解希望采用的结构、语气和详细程度。

检查提示词时，可以依次确认：

```text
任务是否明确？
背景信息是否足够？
重要限制是否写清楚？
输出格式是否明确？
不同要求是否互相冲突？
```

## 3. 常见提示方式

### 3.1 零样本提示

只描述任务，不提供示例：

```text
判断下面评论是正面还是负面：这台电脑运行速度很快。
```

### 3.2 少样本提示

提供少量示例，再让模型处理新内容：

```text
“物流很快” → 正面
“电池不耐用” → 负面

“屏幕显示很清楚” →
```

### 3.3 分步骤提示

把复杂任务拆成明确步骤：

```text
1. 找出代码的输入和输出。
2. 解释每个张量的形状。
3. 说明注意力的数据流。
4. 最后总结这一层的作用。
```

### 3.4 提供参考内容

要求模型根据给定资料回答：

```text
请根据下面的代码解释 EncoderLayer，
不要把代码中尚未实现的功能描述成已经完成。
```

清晰的提示词可以提高结果质量，但不能保证内容必然正确。涉及代码、数据、医学、法律或实时信息时，仍然需要验证。

### 3.5 提示词怎样影响模型输出

模型每次生成下一个 token 时，会结合当前能够使用的上下文进行计算。这些上下文通常包括：

```text
系统要求
+ 用户当前的提示词
+ 前面的聊天内容
+ 当前回答中已经生成的内容
```

这些内容会先被拆成 token，再转换成向量交给模型。模型根据完整上下文，为词表中的所有候选 token 计算分数和概率：

```text
提示词 + 聊天上下文
        ↓
拆分成 token 并转换成向量
        ↓
模型理解当前完整上下文
        ↓
计算下一个 token 的概率
        ↓
选择一个 token 并追加到上下文
        ↓
继续预测下一个 token
```

因此，同一个模型面对不同提示词时，会得到不同的候选概率。例如：

```text
提示词：请用严谨的科普语言介绍苹果。
```

模型会更倾向于生成：

```text
水果、蔷薇科、营养、果实……
```

如果改成：

```text
提示词：请用儿童故事的方式介绍苹果。
```

模型会更倾向于生成：

```text
从前、小苹果、森林、可爱……
```

提示词不会在一次对话中重新训练或修改模型参数。它作为当前上下文参与计算，从而改变每一步生成时的 token 概率分布。

提示词也不只影响第一个输出 token。每生成一个新 token，它都会加入上下文，模型再结合“原提示词 + 聊天记录 + 已生成内容”预测下一步，所以提示词会持续影响整个回答。

可以简单记成：

```text
提示词决定模型应该往哪个方向回答
生成参数决定模型选词时有多稳定或多随机
```

提示词通常属于软约束：它能让某类输出的概率升高，但不一定百分之百保证格式、字数或内容完全符合要求。必须严格满足的条件，还需要程序校验、结构化输出或长度限制等硬约束。

### 3.6 思维链与任务分解

思维链（Chain of Thought，CoT）是一类用于复杂任务的提示方法。它的基本思想是：不要让模型从问题直接跳到答案，而是引导模型先拆分问题、处理关键中间步骤，再形成结论。

例如，下面的要求只给出了最终目标：

```text
分析这段程序为什么运行失败，并给出修复方案。
```

可以改成有步骤的任务：

```text
1. 根据错误信息定位失败位置。
2. 结合相关代码判断根本原因。
3. 排除与现象不符的可能性。
4. 给出最小修改方案。
5. 说明怎样验证修复结果。
```

这种写法的价值在于给复杂任务建立处理顺序：

```text
复杂问题
   ↓
拆成若干较小问题
   ↓
逐步取得中间结果
   ↓
检查中间结果是否一致
   ↓
形成最终答案
```

#### 传统 CoT 提示

传统做法常使用：

```text
请一步一步思考。
请展示完整推理过程。
```

或者提供带有中间步骤的示例，让模型模仿相同的解题结构。这种方式对数学题、逻辑题以及旧一些的普通语言模型有时能够提高正确率。

但是，不能把模型写出的长篇推理当作正确性的保证。模型可能得到正确结论却写出不准确的解释，也可能写出看起来流畅但实际错误的推导。推理文字越长，也不表示模型一定思考得越好。

#### 更实用的现代写法

对于现代推理模型，通常不必强制它展示完整的内部思维过程。更实用的提示是明确：

```text
目标：最终需要解决什么问题
成功标准：什么结果才算完成
上下文：有哪些代码、数据和已知事实
约束：哪些地方不能修改或不能假设
检查项：结果需要通过哪些验证
输出：只展示用户需要检查的关键步骤和结论依据
```

例如：

```text
请诊断这个登录接口返回 401 的原因并给出最小修复。

成功标准：
- 正确密码能够返回 token
- 错误密码仍然返回 401
- 不修改数据库结构

请先检查报错和相关调用链，再给出根因、修改内容和验证结果。
最终回答只保留关键判断依据，不需要展示冗长的内部思考。
```

这样既要求模型认真分解和验证任务，又让输出保持清晰、可检查。当前 OpenAI 模型指南也更强调描述目标、成功标准、约束和证据，让推理模型自行选择有效路径，除非业务确实要求固定处理步骤。[OpenAI Model guidance](https://developers.openai.com/api/docs/guides/latest-model)

#### 哪些情况适合明确步骤？

```text
适合：
- 任务必须按照固定业务流程执行
- 每一步都有需要检查的中间产物
- 计算、诊断或决策容易遗漏条件
- 希望结果便于审查和复现

不必强制：
- 简单问答、翻译或格式转换
- 模型已经能够稳定完成的任务
- 具体步骤并不重要，只关心最终结果
```

#### CoT 与普通分步骤指令的区别

两者关系很近，但侧重点不同：

| 方法 | 主要目的 |
|---|---|
| CoT | 引导模型进行中间推理，再得到答案 |
| 任务分解 | 明确任务应该完成哪些阶段和产物 |
| 检查清单 | 防止遗漏约束、边界和验证 |

在真实开发工作中，三者经常组合使用：

```text
先定位现象
→ 分析根因
→ 设计最小修改
→ 执行验证
→ 汇报关键依据和结果
```

可以简单记成：

> 复杂任务不要只说“给我答案”，而要提供目标、背景、约束和成功标准；当处理顺序确实重要时，再明确要求按步骤分析、验证并汇报关键依据。

## 4. 模型怎样生成下一个 token

### 4.1 为什么需要分词

大语言模型不能直接理解文字，它的核心计算处理的是数字和向量。因此，一段文字进入模型之前，必须先经过分词器（Tokenizer）：

```text
自然语言文本
    ↓ 分词
token 序列
    ↓ 查询词表
token ID 序列
    ↓ Embedding
模型能够计算的向量
```

这个将文本拆成 token 并转换为数字 ID 的过程，叫作分词（Tokenization）。

Token 是模型处理文本的基本单位，但它不一定等于人类理解的一个“词”。一个 token 可能是：

```text
一个完整单词
一个单词片段
一个汉字
一个标点
一个空格与单词的组合
一个或多个字节片段
```

之所以需要专门设计分词方法，是因为按完整单词切分和按单个字符切分都有明显问题。

#### 按完整单词分词的问题

按词分词看起来最自然：

```text
Datawhale agent learns
↓
["Datawhale", "agent", "learns"]
```

完整单词通常包含较完整的语义，而且产生的序列较短。但是它有两个主要问题。

第一个问题是词表会非常大。一个语言中存在大量词语、词形变化、人名、地名、专业术语和拼写组合。如果每个完整单词都占据一个词表位置，词表会迅速膨胀。

例如：

```text
look
looks
looked
looking
```

如果按完整单词切分，它们会成为四个互不相同的 token。模型不容易直接复用它们共同包含的 `look`。

第二个问题是未登录词（Out-Of-Vocabulary，OOV）。如果一个新词没有被收入词表，分词器就无法找到对应的 token。例如词表中存在：

```text
Datawhale
Agent
```

却不一定存在新组合：

```text
DatawhaleAgent
```

如果只允许使用完整单词，模型就可能无法表示这个新词。

#### 按单个字符分词的问题

另一种方法是把文本全部拆成单个字符：

```text
looking
↓
["l", "o", "o", "k", "i", "n", "g"]
```

这种方式的词表很小，并且几乎可以组合出所有文字，不容易出现 OOV。但是它也有两个问题。

第一，序列会变得很长：

```text
按完整单词：looking → 1 个 token
按字符：    looking → 7 个 token
```

序列越长，越占用模型的上下文窗口，也需要更多计算。

第二，单个字符的语义通常很弱。模型还要额外学习：

```text
l + o + o + k 怎样组成 look
look + ing 怎样表示正在进行的动作
```

这会降低学习效率。

#### 子词分词的折中方案

现代大语言模型通常采用子词分词（Subword Tokenization），在完整单词和单个字符之间取得平衡：

```text
常见词或常见片段：尽量使用较大的 token
少见词或新词：    拆成多个较小 token 组合
```

例如，分词器可能学习到：

```text
look
ing
ed
s
```

于是：

```text
look    → ["look"]
looking → ["look", "ing"]
looked  → ["look", "ed"]
looks   → ["look", "s"]
```

这样既可以复用共同的 `look`，又不需要把所有词形变化都作为完整 token 存入词表。

对于没见过的新词，也可以通过较小单位组合：

```text
词表中没有完整的 bug
但存在 b 和 ug
所以 bug → ["b", "ug"]
```

三种方式可以对比为：

| 分词方式 | 优点 | 主要问题 |
|---|---|---|
| 按完整单词 | 序列短，单个 token 语义较完整 | 词表巨大，容易出现 OOV，近似词形难以复用 |
| 按单个字符 | 词表小，几乎能表示任意文本 | 序列长，单个 token 语义弱 |
| 按子词 | 平衡词表大小、序列长度和新词表示能力 | 切分结果取决于具体分词器，有时不符合人类直觉 |

#### 分词为什么会影响实际使用？

模型的上下文长度和 API 用量通常按照 token 数量计算，而不是按照汉字数、单词数或字符串长度计算。因此，同一段文字使用不同分词器时，可能得到不同的 token 数量。

分词会直接影响：

```text
上下文窗口：一段内容会占用多少输入空间
计算与成本：输入和输出包含多少 token
模型表现：同一内容采用不同切分方式时，模型看到的基本单位不同
```

例如：

```text
2 + 2
2+2
```

它们在人类看来含义相同，但空格不同可能导致分词结果不同。英文大小写、特殊符号、中英文混合文本和代码标识符也可能产生不同 token 序列。

所以，分词的目标可以概括为：

> 把任意文本稳定地转换成模型可处理的有限数字序列，同时在词表大小、序列长度和语义表达之间取得平衡。

以上内容根据 [Hello-Agents 第三章“大语言模型基础”中的文本分词章节](https://github.com/datawhalechina/hello-agents/blob/main/docs/chapter3/%E7%AC%AC%E4%B8%89%E7%AB%A0%20%E5%A4%A7%E8%AF%AD%E8%A8%80%E6%A8%A1%E5%9E%8B%E5%9F%BA%E7%A1%80.md) 整理。

### 4.2 Token 与 BPE 字节对编码

大语言模型不能直接处理文字，需要先通过分词器把文本拆成 token，再把每个 token 转换成数字 ID。

```text
原始文字
   ↓ Tokenizer
token 序列
   ↓ 查找词表
token ID 序列
   ↓ Embedding
向量序列
   ↓
交给模型计算
```

Token 不一定是一个完整单词，也可能是单个字符、常见子词、标点或字节片段。例如：

```text
h、u、g：单个字符 token
ug、un：常见子词 token
pug、pun：恰好也是完整单词的 token
```

BPE（Byte Pair Encoding，字节对编码）的核心规则是：

> 统计当前语料表示中所有相邻 token 对的频率，每次将高频的一对合并成一个新 token，并加入词表。

#### 训练语料和初始词表

假设用于训练分词器的迷你语料为：

```text
{"hug": 1, "pug": 1, "pun": 1, "bun": 1}
```

它表示：

```text
hug 出现 1 次
pug 出现 1 次
pun 出现 1 次
bun 出现 1 次
```

这里有 4 个完整单词。初始阶段把它们拆成字符 token：

```text
hug → h u g
pug → p u g
pun → p u n
bun → b u n
```

找出所有不同字符，得到初始词表：

```text
{h, u, g, p, n, b}
```

初始词表大小为 6。这里的 6 表示词表中有 6 种基础 token，不是语料中有 6 个完整单词。

#### 第一次合并：u + g → ug

初始语料中的相邻 token 对包括：

```text
hug：h+u、u+g
pug：p+u、u+g
pun：p+u、u+n
bun：b+u、u+n
```

其中 `u+g` 分别出现在 `hug` 和 `pug` 中，所以频率为 2。按照图中的合并顺序，将它们合并成新 token：

```text
u + g → ug
```

词表增加 `ug`，大小从 6 变成 7：

```text
{h, u, g, p, n, b, ug}
```

语料中的 token 表示随之改变：

```text
hug → h ug
pug → p ug
pun → p u n
bun → b u n
```

原始单词和含义没有变化，只是 `hug` 和 `pug` 内部相邻的 `u g` 改用一个 token `ug` 表示。`pun` 和 `bun` 中不存在 `u g`，所以本轮保持不变。

#### 第二次合并：u + n → un

重新统计更新后的语料，`u+n` 在 `pun` 和 `bun` 中各出现一次，总频率为 2：

```text
u + n → un
```

词表增加 `un`，大小变成 8：

```text
{h, u, g, p, n, b, ug, un}
```

语料表示变成：

```text
hug → h ug
pug → p ug
pun → p un
bun → b un
```

#### 第三、四次合并

继续按照图中的合并顺序：

```text
第 3 次：p + ug → pug，频率 1，词表大小变成 9
第 4 次：p + un → pun，频率 1，词表大小变成 10
```

完整过程如下：

| 步骤 | 选择的相邻 token 对 | 频率 | 合并结果 | 词表大小 |
|---|---|---:|---|---:|
| 初始化 | — | — | `{h, u, g, p, n, b}` | 6 |
| 合并 1 | `u + g` | 2 | `ug` | 7 |
| 合并 2 | `u + n` | 2 | `un` | 8 |
| 合并 3 | `p + ug` | 1 | `pug` | 9 |
| 合并 4 | `p + un` | 1 | `pun` | 10 |

最终词表可以表示为：

```text
{h, u, g, p, n, b, ug, un, pug, pun}
```

“词表大小为 10”表示分词器最终可以直接使用 10 种 token，不表示语料中有 10 个完整英文单词。

#### 为什么每次只合并相邻的两个 token？

BPE 中的 `Pair` 就是“一对”。算法通过重复进行两两合并，逐步构造更长的 token：

```text
u + g  → ug
p + ug → pug
```

虽然每次只合并两个已有 token，经过多轮后仍然可以得到由三个或更多字符组成的 token。这样做还能优先保留可复用的片段：

```text
ug 可以用于 hug、pug、bug、mug、rug……
```

如果一开始只建立完整的 `pug`，它就无法帮助表示其他包含 `ug` 的新词。

基础字符词表本来已经可以组合出语料中的所有单词，BPE 合并的主要目的不是让文本“能够被表达”，而是让常见文本使用更少的 token 表示：

```text
合并前：hug → h + u + g，使用 3 个 token
合并后：hug → h + ug，使用 2 个 token
```

#### 使用训练好的 BPE 处理新词

训练结束后，处理新文本时不会重新统计频率，而是应用已经学到的合并规则。

例如新词 `bug`：

```text
初始拆分：b u g
已有规则：u + g → ug
应用规则：b ug
最终结果：["b", "ug"]
```

虽然训练语料中没有完整的 `bug`，分词器仍然能用较小 token 组合表示它。

需要区分两个阶段：

```text
训练分词器：从语料中统计频率，学习词表和合并规则
使用分词器：直接应用已有规则，把新文本转换成 token ID
```

一句话总结：

> BPE 从基础单位开始，反复合并语料中高频的相邻 token 对，使常见片段使用更大的 token 表示，同时保留小 token 来组合没有见过的新词。

模型不是一次写出完整答案，而是不断预测下一个 token：

```text
已有内容
    ↓
为词表中的所有候选 token 计算分数
    ↓
将分数转换成概率
    ↓
按照采样策略选择一个 token
    ↓
把它追加到已有内容后面
    ↓
继续预测
```

假设模型得到以下候选概率：

| 排名 | 候选 token | 概率 |
|---:|---|---:|
| 1 | 苹果 | 40% |
| 2 | 香蕉 | 25% |
| 3 | 西瓜 | 15% |
| 4 | 汽车 | 10% |
| 5 | 天空 | 6% |
| 6 | 跑步 | 4% |

`Temperature`、`Top-k` 和 `Top-p` 不负责理解提示词，也不修改模型已经学到的知识。它们控制的是：

> 面对已经得到的候选分数，最终怎样选择下一个 token？

## 5. Temperature

Temperature 会在 softmax 之前调整高分和低分候选之间的差距。

```text
温度较低：放大分数差距，更倾向最高概率候选
温度较高：缩小分数差距，让低概率候选获得更多机会
```

| Temperature | 通常表现 |
|---|---|
| 较低 | 更稳定、更确定，更容易重复选择高概率 token |
| 较高 | 更多样，但也更容易产生错误或不连贯内容 |

温度升高不代表模型进行了更深入的思考，只是增加了低概率 token 被抽中的机会。温度降低也不是让模型“更像预训练内容”，而是让模型更坚定地选择自己原本评分最高的候选。

可以记成：

> Temperature 调整的是所有候选之间的概率差距，不负责删除候选。

## 6. Top-k

Top-k 按照概率从高到低排序，只保留固定数量的前 `k` 个候选。

例如：

```text
top_k = 3
```

只保留：

```text
苹果：40%
香蕉：25%
西瓜：15%
```

其余候选的概率变成 0。保留下来的概率总和为 80%，所以需要重新归一化：

```text
苹果：40 ÷ 80 = 50%
香蕉：25 ÷ 80 = 31.25%
西瓜：15 ÷ 80 = 18.75%
```

最后只从这三个候选中采样。

Top-k 可以记成：

> 不管模型当前是否确定，固定只让概率最高的前 k 名进入候选集合。

## 7. Top-p

Top-p 也叫核采样。它不固定保留几个候选，而是先按照概率从高到低排序，再逐个累加，直到累计概率第一次达到或超过 `p`。

例如：

```text
top_p = 0.8
```

累加过程：

```text
苹果：                40%
苹果 + 香蕉：         65%
苹果 + 香蕉 + 西瓜：  80%  ← 达到阈值，停止加入
```

最终保留：

```text
苹果、香蕉、西瓜
```

然后对这些候选重新归一化并采样。

这里的 `p` 不是某一个词必须达到的分数，而是所有保留候选的累计概率阈值。

Top-p 可以记成：

> 不固定保留多少个词，只保留一组累计概率足够高的候选词。

## 8. Top-k 和 Top-p 的区别

最直接的理解是：

```text
Top-k 按候选词数量筛选
Top-p 按候选词的累计概率筛选
```

| 参数 | 保留规则 | 候选数量 |
|---|---|---|
| Top-k | 固定保留概率最高的前 k 个 | 固定 |
| Top-p | 保留累计概率达到 p 的候选 | 动态变化 |

### 模型很确定时

```text
苹果：80%
香蕉：10%
西瓜：5%
其他：5%
```

若 `top_p=0.9`：

```text
苹果 + 香蕉 = 90%
```

只需要保留两个候选。

### 模型不确定时

```text
苹果：25%
香蕉：20%
西瓜：18%
汽车：15%
天空：12%
跑步：10%
```

若 `top_p=0.9`，需要累加前五个候选才能达到 90%，所以保留五个。

因此：

```text
Top-k：无论模型是否确定，都保留固定数量
Top-p：模型越确定，候选越少；模型越不确定，候选越多
```

## 9. 三个参数怎样配合

| 参数 | 作用 | 简单记忆 |
|---|---|---|
| Temperature | 调整高低分候选之间的差距 | 调整概率的平坦程度 |
| Top-k | 固定保留前 k 个候选 | 固定人数 |
| Top-p | 保留累计概率达到 p 的候选 | 固定累计概率 |

一种常见的概念流程是：

```text
模型输出原始分数
        ↓
Temperature 调整分数差距
        ↓
Softmax 转换成概率
        ↓
Top-k / Top-p 筛选候选集合
        ↓
对保留候选重新归一化
        ↓
按照剩余概率采样一个 token
```

Top-k 和 Top-p 可以同时使用。此时最终候选集合同时受到“最多保留多少名”和“累计概率达到多少”的限制。具体系统可能只开放部分参数，也可能采用不同的处理顺序。

参数没有绝对正确的设置，需要根据任务权衡：

```text
事实问答、代码和数据提取：通常更重视稳定性
故事、创意表达和头脑风暴：通常可以接受更多样性
```

这些是一般规律，并不表示所有模型和服务都使用完全相同的参数范围与实现。

## 10. 模型幻觉

模型幻觉（Hallucination）是指：

> 模型生成了看起来合理、语言也很流畅，但实际上错误、与输入矛盾或没有可靠依据的内容。

模型擅长根据已有 token 预测下一个合适的 token，但“语言上最像答案”并不等于“事实一定正确”。例如：

```text
用户：请告诉我某篇不存在的论文是谁写的。
模型：这篇论文由某某教授于 2020 年发表……
```

回答的语法和格式可能非常自然，但论文、作者和年份都是模型根据常见表达组合出来的，并没有真实依据。

### 10.1 幻觉的主要类型

为了避免分类层级混乱，可以先分成两大类：

```text
模型幻觉
├── 事实性幻觉：与现实世界的事实不符
└── 忠实性幻觉：没有忠实依据给定的输入内容
    ├── 内在幻觉：与输入直接矛盾
    └── 外在幻觉：添加输入没有提供、也无法推导的信息
```

#### 事实性幻觉

事实性幻觉是指模型的回答与客观事实不一致。

```text
问题：爱因斯坦是哪一年出生的？
错误回答：爱因斯坦出生于 1885 年。
```

爱因斯坦实际出生于 1879 年，因此这个回答与现实事实冲突。

事实性主要检查：

> 模型说的内容与真实世界是否一致？

#### 忠实性幻觉

忠实性幻觉是指模型没有严格依据用户提供的文章、数据、代码或上下文回答。

忠实性主要检查：

> 模型说的内容是否能够从当前输入材料中得到支持？

忠实性幻觉可以继续分成内在幻觉和外在幻觉。

##### 内在幻觉

内在幻觉是模型回答与输入内容直接矛盾。

```text
输入资料：小明今年 20 岁。
模型回答：小明今年 25 岁。
```

输入明确写了 `20 岁`，回答却说 `25 岁`，两者直接冲突。

##### 外在幻觉

外在幻觉是模型增加了输入中没有提供、也不能从输入中推导出来的信息。

```text
输入资料：小明今年 20 岁。
模型回答：小明今年 20 岁，目前在北京大学学习计算机。
```

`20 岁` 有资料支持，但“在北京大学学习计算机”没有出处。它没有直接违背原文，却是模型自行补充的内容。

三者可以这样区分：

| 类型 | 判断依据 | 示例问题 |
|---|---|---|
| 事实性幻觉 | 是否符合现实世界 | 真实年份、人物、地点是否正确？ |
| 内在幻觉 | 是否与输入直接矛盾 | 原文说 20 岁，回答是否说成 25 岁？ |
| 外在幻觉 | 是否添加无依据的信息 | 原文没提学校，回答是否擅自补充学校？ |

同一个回答有时可能同时属于多个类型。例如回答既违反了用户提供的资料，也违反了现实事实，就可以同时具有事实性和忠实性问题。

### 10.2 幻觉产生的原因

幻觉通常不是由单一原因造成的，可以从数据、训练目标、生成过程和输入上下文几个方面理解。

#### 原因一：训练数据存在错误、冲突或缺失

预训练数据可能包含：

```text
错误信息
已经过时的信息
彼此矛盾的资料
重复或低质量内容
某些领域缺少足够资料
```

如果训练数据本身有问题，模型就可能学习到错误或互相冲突的规律。

此外，模型不是把所有训练资料原样存进一个可以随时查询的数据库。知识会分散地学习到大量模型参数中，因此即使训练数据中存在正确答案，模型也不一定能在每次生成时准确地使用它。

#### 原因二：训练目标是预测下一个 token，而不是验证事实

大语言模型预训练时主要学习：

```text
根据前面的 token
预测接下来最可能出现什么 token
```

这个目标会让模型擅长生成连贯、自然、形式上像答案的文字，但它没有天然执行下面这些操作：

```text
先查询可靠资料
再核对事实真假
找不到答案时必须说不知道
为每句话提供真实出处
```

因此必须区分：

```text
高概率的表达 ≠ 已经验证的事实
语言非常流畅 ≠ 内容一定正确
```

#### 原因三：自回归生成会让前面的错误影响后面

模型一次生成一个 token，并把新 token 加入上下文，再继续预测：

```text
已有内容
   ↓
预测一个新 token
   ↓
加入已有内容
   ↓
继续预测下一个 token
```

如果中间选择了错误 token，后续生成就会以这个错误内容作为新的上下文。

```text
正确方向：爱因斯坦出生于 1879 年……
错误生成：爱因斯坦出生于 1885 年……
                              ↓
后面的内容继续围绕 1885 年组织
```

模型通常会努力让后文与已经生成的内容保持连贯，而不会自动回头删除前面的错误。这就是错误逐步传播或“滚雪球”的现象。

需要注意，模型不一定总是选择概率最高的 token：

```text
do_sample=False：通常选择概率最高的候选
do_sample=True： 从筛选后的候选中随机采样
```

提高 `Temperature` 或扩大 `Top-k`、`Top-p` 的候选范围，可能增加表达多样性，同时也可能提高选中不可靠 token 的机会。不过即使关闭随机采样，概率最高的 token 本身也可能是错误的，所以确定性生成不能彻底消除幻觉。

#### 原因四：提示词含糊或提供的信息不足

例如：

```text
苹果什么时候发布？
```

这里的“苹果”可能指苹果公司的产品，也可能指水果。问题没有给出产品名称和年份，模型可能根据常见表达自行猜测用户的意思。

当问题缺少必要背景、存在歧义或包含错误前提时，模型更容易沿着错误方向生成内容。

#### 原因五：上下文过长或关键信息没有被有效利用

即使答案已经出现在输入材料中，如果资料很长、信息互相干扰，或者关键内容不突出，模型也可能没有正确使用它，转而依赖预训练中不完整的知识回答。

这时可能出现：

```text
漏掉关键条件
混淆不同段落的信息
使用模型原有知识覆盖用户提供的资料
```

#### 原因六：问题超出模型的知识边界

模型可能不知道：

```text
训练数据截止时间之后发生的事情
非常冷门或没有公开的信息
公司内部和个人私有数据
没有提供给模型的本地文件内容
需要实时查询才能确定的信息
```

模型无法直接意识到自己究竟缺少哪些知识。有时它会用相似的语言模式补全一个听起来合理的答案，而不是明确回答“不知道”。

#### 原因七：指令微调可能让模型倾向于积极回答

聊天模型通常被训练成有帮助、礼貌并尽量回答问题。这种倾向可能产生一个副作用：

```text
没有足够依据时
模型仍然尝试给出完整答案
```

因此，回答得完整、自信，也不能证明内容可靠。

可以把这些原因串成一条完整链路：

```text
训练数据可能存在错误或知识缺口
              ↓
模型学习的是 token 概率规律，而不是事实数据库
              ↓
提示词可能含糊，上下文也可能没有被正确利用
              ↓
生成时某一步选中错误或无依据的 token
              ↓
错误 token 被加入上下文并影响后续生成
              ↓
最终形成语言流畅但内容错误的回答
```

### 10.3 怎样降低幻觉

降低幻觉可以从训练阶段、使用阶段和验证阶段同时入手。

#### 方法一：提高预训练数据质量

在训练模型之前，对原始数据进行处理：

```text
收集原始数据
    ↓
去除重复、乱码和广告内容
    ↓
过滤错误、过时和低质量信息
    ↓
尽量处理彼此矛盾的资料
    ↓
使用整理后的数据训练模型
```

这能减少模型从训练数据中学到错误规律的机会，但不能完全避免幻觉。互联网中的资料数量巨大、质量不一，而且现实信息会不断变化，不可能逐条保证永远正确。

#### 方法二：使用 RAG 提供外部资料

RAG（检索增强生成）可以先从知识库中查找相关内容，再把查到的资料和用户问题一起交给模型：

```text
用户提出问题
    ↓
从知识库检索相关资料
    ↓
把“问题 + 检索资料”交给模型
    ↓
要求模型根据资料组织回答
```

例如，用户询问公司的请假制度时：

```text
没有 RAG：模型依靠预训练知识猜测一般公司的制度
使用 RAG：先查询本公司的真实规章，再根据规章回答
```

RAG 的本质不是重新训练模型，而是在本次回答的上下文中提供更准确、与问题更相关的依据。

不过，RAG 也不能保证回答一定正确。仍然可能发生：

```text
没有检索到正确资料
检索结果与问题无关
知识库本身存在错误或已经过时
模型误解了检索内容
模型在资料之外擅自补充信息
```

#### 方法三：联网搜索或调用可靠工具

联网搜索与 RAG 的思路相似，区别主要在资料来源：

```text
RAG：通常检索预先建立的内部知识库
联网搜索：查询互联网上可以获得的当前信息
```

联网搜索更适合新闻、天气、价格、软件版本、政策法规等可能发生变化的信息。计算器、数据库和业务接口等工具，则适合提供精确计算结果或系统中的真实数据。

搜索结果本身也可能出错，因此还应该：

```text
优先使用权威来源
检查信息发布日期
对比多个独立来源
区分事实、观点和推测
让回答附带可核验的引用
```

#### 方法四：写清楚提示词和回答边界

可以在提示词中提供明确的问题、背景和时间范围，并要求模型：

```text
只根据给定资料回答
不要补充资料中没有出现的信息
无法从资料确定时明确说“不知道”
标明每个结论对应的依据
```

例如，可以把模糊的要求：

```text
总结这份资料。
```

改成：

```text
请只根据下面提供的资料回答，不要补充资料之外的人物、时间和事件。
每个结论后注明对应的原文段落；如果资料无法支持某个结论，请明确写“资料中未说明”。
```

这里需要注意：要求模型提供来源，只是一种约束，模型仍可能编造来源。真正重要的是让系统连接可验证的资料，并对引用内容进行检查。

#### 方法五：调整生成策略

事实问答、数据提取和代码生成等任务通常更重视准确性，可以适当降低随机性，例如降低 `Temperature`，或关闭随机采样。

但是：

```text
降低随机性 ≠ 消除幻觉
```

即使每次都选择概率最高的 token，这个 token 也可能是错误的。生成参数只能减少某些不稳定输出，不能替代事实验证。

#### 方法六：生成后进行检查

对重要回答还可以增加验证步骤：

```text
检查引用是否真实存在
使用程序校验数字、日期和格式
把复杂任务拆开，检查关键中间结果
让另一个验证步骤对照原文查找矛盾
在医疗、法律、金融等高风险场景进行人工审核
```

整个降低幻觉的流程可以概括为：

```text
高质量训练数据
      ↓
清晰的提示词和回答边界
      ↓
RAG、搜索、数据库或工具提供可靠依据
      ↓
模型生成回答
      ↓
程序校验、来源核对或人工审核
```

#### 幻觉能否彻底消除？

目前很难彻底消除。语言模型的核心任务仍然是根据上下文预测下一个 token，而不是天然保证每一个 token 都经过事实验证：

```text
概率最高的 token ≠ 一定符合事实
语言非常流畅      ≠ 内容经过验证
使用 RAG 或搜索    ≠ 模型一定正确使用资料
关闭随机采样       ≠ 不会产生幻觉
```

因此，更现实的目标是：

> 通过数据清洗、训练与对齐、RAG、联网搜索、工具调用、提示词约束和结果审核，降低幻觉发生的概率，并减少幻觉带来的风险。

一句话总结：

> 模型幻觉的根本问题是，模型的目标是生成在当前上下文中高概率、看起来合理的 token，而不是天然保证每个 token 都经过事实验证；现有方法可以降低幻觉，但不能保证彻底消除。

## 11. 最终总结

提示词工程与生成参数分别控制两个阶段：

```text
提示词工程：让模型更清楚地理解任务
生成参数：  控制模型怎样从候选 token 中选择输出
```

清晰提示词通常包括：

```text
任务 + 背景 + 约束 + 输出格式 + 必要示例
```

三个生成参数可以记成：

```text
Temperature：调整候选之间的概率差距
Top-k：       固定保留前 k 个候选
Top-p：       动态保留累计概率达到 p 的候选
```

最短记忆：

> Temperature 调差距，Top-k 固定候选数量，Top-p 固定候选累计概率。

模型幻觉可以记成：

> 模型生成得像正确答案，不代表答案已经被事实证明；可靠应用需要为模型提供依据，并对关键结果进行验证。
